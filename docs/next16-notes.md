# Next.js 16.2.10 — dense digest for coding against THIS repo

Verified against `node_modules/next/dist/docs`. This is React 19.2 + App Router + Turbopack-by-default.
If it contradicts your training data, THIS wins. Node 20.9+, TS 5.1+.

## 0. The 5 things that will bite you
1. **`params`, `searchParams`, `cookies()`, `headers()`, `draftMode()` are ALL async now** — synchronous access was fully removed in 16. You MUST `await` them (or `use()` them in Client Components).
2. **Turbopack is the default** for `next dev` AND `next build` (no `--turbopack` flag). A custom `webpack` config in `next.config.ts` will **fail the build**. We don't have one — keep it that way, or a dep might inject one.
3. **Route Handlers are dynamic by default & NOT cached.** Read bodies with Web APIs (`request.json()/.text()/.arrayBuffer()/.formData()`). No `bodyParser`, and **no built-in body-size limit** (unlike old Pages API routes). Good for GLB uploads.
4. **`next/dynamic` with `ssr:false` only works INSIDE a Client Component** (`'use client'`). Using it in a Server Component throws a build error. This is the pattern for Three.js.
5. **`next lint` is gone** — `next build` no longer runs ESLint. Lint won't block builds. `.next/dev` is the dev output dir (dev & build can run concurrently; a lockfile blocks two `next dev`).

## 1. App Router pages & layouts
- `app/**/page.tsx` = a route; `layout.tsx` wraps children. Server Components BY DEFAULT (can be `async`).
- Dynamic segment folder `app/s/[id]/page.tsx`. `params` is a **Promise**:
```tsx
// Server Component page
export default async function Page({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params
  return <div>{id}</div>
}
```
- Typed helpers auto-generated by `next dev`/`next build`/`next typegen` and globally available (no import): `PageProps<'/s/[id]'>`, `LayoutProps<'/s/[id]'>`, `RouteContext<'/api/x/[id]'>`.
- `searchParams` (page only) is also `Promise<{ [k]: string | string[] | undefined }>`.
- Metadata: `export const metadata: Metadata = {...}` OR `export async function generateMetadata()`. Server Components only. `import type { Metadata } from 'next'`.

## 2. Client Components (`'use client'`)
- Needed for: `useState`/`useEffect`/hooks, event handlers (`onClick`), browser APIs (`window`, `localStorage`, `navigator`, canvas/WebGL), React Context providers.
- `'use client'` at the very top of the file (above imports) marks a **boundary**: every module it imports & every component it renders directly ships to the client. You don't repeat it in children.
- A Server Component **cannot** pass non-serializable props (functions, class instances) to a Client Component. Pass data; pass Server Components as `children`/props to interleave.
- Context providers must live in a Client Component; render them in `layout.tsx` around `{children}`.
- Client Component page reading a dynamic param:
```tsx
'use client'
import { use } from 'react'
export default function Page({ params }: { params: Promise<{ id: string }> }) {
  const { id } = use(params)      // or useParams() hook anywhere in the tree
}
```
- Env vars: only `NEXT_PUBLIC_*` reach the client bundle; anything else becomes `""` client-side. Keep `OPENAI_API_KEY` server-only (route handlers).

## 3. Route Handlers (`app/api/**/route.ts`) — our API layer
- Export named async funcs per verb: `GET POST PUT PATCH DELETE HEAD OPTIONS`. Web `Request`→`Response`.
- Not cached by default; runs at request time. No config needed for bodies (no `bodyParser`, no `export const config`).
```ts
import type { NextRequest } from 'next/server'
export async function POST(req: NextRequest) {
  const body = await req.json()                 // JSON body
  // const buf = await req.arrayBuffer()         // raw bytes (GLB upload) -> new Uint8Array(buf)
  // const form = await req.formData()           // multipart
  // const q = req.nextUrl.searchParams.get('x') // query params
  return Response.json({ ok: true })            // Response.json helper
}
```
- **Dynamic route params** are a Promise here too:
```ts
export async function GET(req: NextRequest, ctx: { params: Promise<{ id: string }> }) {
  const { id } = await ctx.params
  return Response.json({ id })
}
// or: (req: NextRequest, ctx: RouteContext<'/api/scan/[id]'>) => await ctx.params
```
- **Body size**: no framework limit in route handlers — fine for multi-MB `.glb`. (Server Actions, which we're NOT using, cap at 1MB.) Behind a tunnel/proxy the proxy may impose its own limit.
- `cookies()`/`headers()` from `next/headers` are async & read-only inside handlers.
- CORS / custom headers: return `new Response(body, { headers: {...} })`.

## 4. Streaming responses / SSE (for narration + LLM token streams)
Return a `ReadableStream` as the Response body. This is the SSE pattern:
```ts
export async function GET() {
  const encoder = new TextEncoder()
  const stream = new ReadableStream({
    async start(controller) {
      controller.enqueue(encoder.encode(`data: ${JSON.stringify({ text: 'hi' })}\n\n`))
      // ...loop, await work, enqueue more...
      controller.close()
    },
  })
  return new Response(stream, {
    headers: {
      'Content-Type': 'text/event-stream',      // for SSE; use text/plain for raw chunks
      'Cache-Control': 'no-cache, no-transform',
      Connection: 'keep-alive',
      'X-Accel-Buffering': 'no',                 // stop nginx/proxy buffering
    },
  })
}
```
- SSE frame format is `data: <payload>\n\n`. Consume with `EventSource` (GET only) or `fetch()` + `res.body.getReader()` (works with POST).
- Once the first chunk is sent, **status & headers are locked** — you can't switch to 4xx/5xx mid-stream. Validate & bail BEFORE streaming starts.
- Compression/proxies can buffer; send `Accept-Encoding: identity` from a test client to observe chunks. Turbopack/Node server support streaming.

## 5. `next/dynamic` + `ssr:false` (Three.js / WebGL viewer)
- `ssr:false` is **not allowed in a Server Component** — build error "ssr: false is not allowed with next/dynamic in Server Components. Please move it into a Client Component."
- Correct pattern: a thin `'use client'` wrapper does the dynamic import.
```tsx
'use client'
import dynamic from 'next/dynamic'
const RoomViewer = dynamic(() => import('./RoomViewer'), {
  ssr: false,
  loading: () => <p>Loading 3D…</p>,
})
export default function ViewerClient(props) { return <RoomViewer {...props} /> }
```
- The import path must be a static string literal inside `dynamic()`. Named export: `dynamic(() => import('./x').then(m => m.Thing))`.
- For loading libs on demand inside an event handler: `const THREE = await import('three')`.

## 6. Static files & images
- Anything in `public/` is served from `/`. `public/sample-room.glb` → fetch at `/sample-room.glb`. GLBs, models, etc. are served as-is (no processing) — load with three's `GLTFLoader`.
- `next/image` optimizes rasters only; **do not** route 3D assets through it. For local raster query-strings you'd now need `images.localPatterns`. Remote images need `images.remotePatterns` (`images.domains` is deprecated). `qualities` now defaults to `[75]`. Not relevant to GLB.
- To pass an uploaded GLB to the client without `public/`, store it (blob/URL) and hand the client a URL or ArrayBuffer.

## 7. Dev vs build behavior
- `npm run dev` (Turbopack) writes to `.next/dev`; `npm run build` writes to `.next`. They can run at once.
- No lint on build. Type errors DO fail `next build` (tsconfig `strict`).
- `process.argv` no longer contains `'dev'` during `next dev` (config loads once). Use `NODE_ENV === 'development'` if you must branch.
- Route/`RouteContext`/`PageProps` types are generated on first `dev`/`build`/`typegen` — a fresh checkout may show missing global types until then; `npx next typegen` regenerates.

## 8. Misc removals/renames (avoid these)
- `middleware.ts` → `proxy.ts` (nodejs runtime only). We likely don't need it.
- `serverRuntimeConfig`/`publicRuntimeConfig` removed → use env vars; `connection()` from `next/server` forces runtime `process.env` read.
- Parallel-route slots now require a `default.js`. `revalidateTag` needs a 2nd arg. `experimental.ppr` gone (use `cacheComponents`). None needed for this build.
- `scroll-behavior: smooth` is no longer auto-overridden on nav; add `data-scroll-behavior="smooth"` to `<html>` if you want the old behavior.
